# HISE CSS diagnostics implementation plan

## Objective

Add HISE-specific compatibility diagnostics to `simple_css::Parser` so an AI agent can write ordinary CSS, run
`diagnose_css`, and receive the implementation details that differ from browser CSS.

The parser must report three distinct outcomes:

- Errors for malformed CSS that prevents correct parsing.
- Warnings for declarations or syntax that are rejected, ignored, unknown, or ineffective.
- Hints for valid declarations whose HISE behavior differs materially from browser CSS.

The HISE-specific knowledge must be authored as tracked JSON in the API generator submodule and embedded into the
binary as a serialized `juce::ValueTree`, following the existing scripting API documentation pattern. The generated
ValueTree and C++ byte array are the runtime representation.

The primary agent workflow is:

1. Generate CSS using ordinary CSS knowledge.
2. Run `hise-cli script diagnose_css <file>`.
3. Correct errors and warnings.
4. Review HISE compatibility hints.
5. Apply or compile the stylesheet only after diagnosis.

## Design principles

### The parser remains authoritative

The embedded records do not implement CSS parsing. `simple_css::Parser` remains responsible for deciding whether
syntax is accepted, ignored, or rejected. The records enrich parser output with stable diagnostic IDs, explanations,
and suggestions.

### Diagnostics are demand-driven

Only report information for syntax found in the stylesheet. Do not inject the complete CSS reference into agent
context and do not return descriptions for ordinary supported declarations.

### Hints are syntax-driven and unconditional

The parser must not inspect runtime component types, flex hierarchies, LookAndFeel ownership, or other integration
context to decide whether to emit a hint. If matching syntax appears, emit the hint and describe all relevant HISE
behaviors defensively in one message. Deduplication keeps this conservative approach inexpensive.

The agent using the stylesheet is responsible for deciding which branch of the hint applies to its usage.

### Valid but surprising behavior is not a warning

Hints must not make diagnosis fail. A hint tells the caller that a declaration is effective but behaves differently
from browser CSS. Warnings remain reserved for syntax that cannot reliably produce the requested result.

### Runtime documentation is structured

The parser must expose structured diagnostics. REST and CLI consumers must not parse line and column information
back out of formatted strings.

### No frontend cost

The diagnostic prose and generated byte array are development tools. They must be excluded from exported plugins
and project DLLs using the appropriate backend or CSS debug-tool guard.

### One stable diagnostic identity

Every diagnostic record must have a stable ID such as:

```text
hise.css.margin.internal-inset
hise.css.overflow.no-effect
hise.css.transform.paint-only
```

The ID is used for deduplication, suppression, tests, CLI formatting, and future documentation links.

## Existing architecture

### Current CSS parser output

`simple_css::Parser` currently exposes:

```cpp
Result parse();
StringArray getWarnings() const;
```

Warnings are formatted with location text such as `Line 4, column 2: ...`. The `/api/parse_css` handler parses this
text back into line, column, and message fields before returning JSON.

Relevant files:

- `hi_tools/simple_css/CssParser.h`
- `hi_tools/simple_css/CssParser.cpp`
- `hi_tools/simple_css/Editor.cpp`
- `hi_tools/simple_css/Renderer.cpp`
- `hi_backend/backend/ai_tools/RestHelpers.cpp`
- `hi_backend/backend/ai_tools/RestHelpers.h`

### Existing diagnostic severity model

`ApiClass::DiagnosticResult` already defines:

```cpp
enum class Severity
{
	OK,
	Unknown,
	Error,
	Warning,
	Info,
	Hint,
	numSeverity
};
```

This is a useful output model, but `simple_css` must not directly depend on the `hi_scripting` API type. The CSS
implementation is in `hi_tools`, while `ApiClass::DiagnosticResult` is in `hi_scripting` and backend-guarded.

The CSS module should define a small local diagnostic type and convert it at integration boundaries.

### Existing embedded API documentation pattern

The scripting API generator performs this pipeline:

```text
authored and generated documentation
    -> filtered records
    -> juce::ValueTree
    -> ValueTree::writeToStream()
    -> generated unsigned char array
    -> ValueTree::readFromData()
    -> lazily cached runtime tree
```

Relevant files:

- `tools/api generator/ApiValueTreeBuilder/Source/Main.cpp`
- `hi_scripting/scripting/api/XmlApi.h`
- `hi_scripting/scripting/api/XmlApi.cpp`
- `hi_scripting/scripting/api/ScriptingApiObjects.cpp`
- `hi_scripting/scripting/api/ScriptingApiObjects.h`

The current API blob uses ValueTree binary serialization without an outer GZIP stream. The CSS diagnostic dataset
should initially use the same mechanism. Add GZIP only if the generated size justifies the extra complexity.

`ApiValueTreeBuilder` currently understands only the scripting API class and method schema. Extend it with a generic
recursive ValueTree mode rather than adding CSS-specific schema knowledge to the C++ builder. A separate Python stage
owns CSS diagnostic validation and converts the human JSON into the generic tree representation.

## Runtime diagnostic model

Add a local type in `simple_css`, with a name such as `Diagnostic` or `ParserDiagnostic`:

```cpp
struct Diagnostic
{
	enum class Severity
	{
		Error,
		Warning,
		Hint
	};

	enum class Classification
	{
		Syntax,
		Support,
		Compatibility
	};

	String id;
	String message;
	StringArray suggestions;
	Severity severity = Severity::Hint;
	Classification classification = Classification::Compatibility;
	int line = 0;
	int column = 0;
	int length = 0;
};
```

The final field names may follow existing HISE conventions, but the type must carry:

- Stable ID.
- Severity.
- Classification.
- Message.
- Suggestions.
- Source position.
- Optional source length.

The parser should expose:

```cpp
const Array<Diagnostic>& getDiagnostics() const;
```

Keep `getWarnings()` temporarily as a compatibility adapter for existing editor consumers. It should format only
warning diagnostics. New consumers must use `getDiagnostics()`.

Fatal parser failures may continue to use `Result` during the first implementation. The REST layer can convert the
failed `Result` into an error diagnostic and append the parser's warning and hint diagnostics. A later cleanup may
move fatal errors into the same structured collection.

## Embedded record schema

The runtime records mirror the output diagnostic fields but also describe when a diagnostic applies.

Suggested ValueTree structure:

```text
CssDiagnostics
  Diagnostic
    id
    severity
    classification
    trigger
    property
    value
    function
    unit
    selector
    message
    deduplicate
    Suggestion
      text
```

Not every property is required for every record. The `trigger` selects which matching fields are meaningful.

### Trigger types

Start with a small explicit trigger enum rather than a general expression language:

```text
property
property-value
function
unit
selector
pseudo-class
pseudo-element
at-rule
```

Examples:

```text
trigger = property
property = margin
```

```text
trigger = property-value
property = display
value = none
```

```text
trigger = unit
unit = rem
```

```text
trigger = function
function = matrix
```

Avoid regex or executable matching expressions in the first version. Add a new explicit trigger type when a real
case cannot be represented by the existing ones.

### Unconditional hint matching

Hints are emitted whenever their syntax trigger matches. The database does not contain consumer filters, omission
records, component predicates, or context-specific severity overrides.

When behavior varies by integration path, the message must state the alternatives. For example, the record for
`display: none` should explain that default-state flex-managed children are hidden, while LookAndFeel and pseudo-state
paint paths only suppress CSS background painting without removing component layout or interaction.

This hint is emitted for every `display: none` declaration and deduplicated by ID. The parser does not attempt to
decide whether the distinction matters to the caller.

Use the same rule for all compatibility hints: make the message universally accurate, emit it based on syntax alone,
and let the agent apply its own project context.

## Severity policy

### Error

Use an error when the stylesheet cannot be parsed correctly.

Examples:

- Unterminated function or quote.
- Missing declaration separator.
- Structurally malformed rule.

Errors should generally remain parser-generated rather than dataset-driven.

### Warning

Use a warning when the declaration cannot reliably produce the requested result.

Examples:

- Unknown property.
- Unsupported transform function.
- Invalid color.
- Recognized property with no rendering effect.
- Declaration ignored because of unsupported syntax.
- `overflow` when no clipping or scrolling occurs.
- Non-solid `border-style` when rendering remains solid.

Warnings must retain the current failure semantics of `diagnose_css`: the stylesheet can parse successfully, but the
caller is told that part of it is ineffective or discarded.

### Hint

Use a hint when the declaration works but HISE semantics differ materially from browser CSS. If behavior varies
between HISE integration paths, describe those paths defensively in the message rather than filtering the hint.

Initial hint candidates include:

- Margins are internal paint insets and do not reserve external flex space.
- `gap` is implemented with synthetic child margins.
- `opacity` does not composite an entire component subtree.
- `position: relative` offsets are ineffective.
- `position: fixed` is local container-relative absolute positioning.
- `display: none` has different behavior in default flex layout and stateful paint paths.
- `rem` behaves like `em`.
- `vh` uses local rectangle height.
- Eight-digit HISE colors are alpha-first.
- URL backgrounds can suppress ordinary fill, border, and shadow painting.
- Transforms affect painting but not layout, clipping, or hit testing.
- Transitions support one tuple and should not be used for continuous relayout.
- Variables do not support fallback arguments or the browser computed-value model.
- Pseudo-state and selector matching do not implement the full browser cascade.

Review each candidate before adding it. Do not automatically convert every `partial` entry from the current CSS
reference into a hint.

## Authoring and generation

### Tracked human source

Store the human-edited records in the API generator submodule:

```text
tools/api generator/css_diagnostics/diagnostics.json
tools/api generator/css_diagnostics/README.md
```

Use a domain-specific JSON schema that is easy to review and does not expose ValueTree serialization details:

```json
{
  "schemaVersion": 1,
  "diagnostics": [
    {
      "id": "hise.css.unit.rem",
      "severity": "hint",
      "classification": "compatibility",
      "trigger": {
        "type": "unit",
        "unit": "rem"
      },
      "message": "HISE resolves rem like em using the supplied local font size. It is not relative to a root font size.",
      "suggestions": [
        "Use em when the local-font-size behavior is intentional."
      ],
      "deduplicate": true,
      "references": [
        "hi_tools/simple_css/CssParser.cpp"
      ]
    }
  ]
}
```

Required authored fields:

- `id`
- `severity`
- `classification`
- `trigger`
- `message`

Optional authored fields:

- `suggestions`
- `deduplicate`
- `references`
- `notes`

`references` and `notes` help maintainers verify the message but are removed from the embedded data.

The existing `guidelines/style/css.json` may be used to extract the first message inventory, but it is not a runtime
or generator input after the authored diagnostic records have been created.

### Python validation and normalization

Add a focused generator script:

```text
tools/api generator/css_diagnostics.py
```

Do not add this independent pipeline to the already large `api_enrich.py`. The script should support:

```text
python css_diagnostics.py validate
python css_diagnostics.py compile
```

The compile command should default to:

```text
input:  css_diagnostics/diagnostics.json
output: enrichment/output/css_diagnostics_tree.json
```

It must:

1. Parse the authored JSON.
2. Validate the schema version.
3. Validate required fields and reject unknown fields.
4. Reject duplicate diagnostic IDs.
5. Validate severity, classification, and trigger names.
6. Validate the fields required by each trigger type.
7. Validate that messages and suggestions are nonempty strings.
8. Strip author-only references and notes.
9. Sort diagnostics deterministically by stable ID.
10. Flatten trigger data into runtime properties.
11. Emit generic recursive ValueTree JSON.

The trigger validator should use an explicit field table:

| Trigger | Required trigger fields |
|---|---|
| `property` | `property` |
| `property-value` | `property`, `value` |
| `function` | `function` |
| `unit` | `unit` |
| `selector` | `selector` |
| `pseudo-class` | `pseudoClass` |
| `pseudo-element` | `pseudoElement` |
| `at-rule` | `atRule` |

Do not add regex or executable trigger expressions in the initial schema.

### Generic ValueTree intermediate

The ignored intermediate file should use one reusable recursive format:

```json
{
  "type": "CssDiagnostics",
  "properties": {
    "schemaVersion": 1
  },
  "children": [
    {
      "type": "diagnostic",
      "properties": {
        "id": "hise.css.unit.rem",
        "severity": "hint",
        "classification": "compatibility",
        "trigger": "unit",
        "unit": "rem",
        "message": "HISE resolves rem like em using the supplied local font size. It is not relative to a root font size.",
        "deduplicate": true
      },
      "children": [
        {
          "type": "suggestion",
          "properties": {
            "text": "Use em when the local-font-size behavior is intentional."
          }
        }
      ]
    }
  ]
}
```

This separates responsibilities cleanly: Python understands the CSS diagnostic schema, while C++ only understands
generic ValueTree serialization.

### ApiValueTreeBuilder extension

Keep the existing three-argument scripting API invocation working. Add a generic mode:

```text
ApiValueTreeBuilder.exe valuetree <input.json> <output_dir> <namespace> <variable>
```

The generic mode recursively creates each node from `type`, copies `properties`, and processes `children`. It should
reject malformed nodes, missing types, unsupported property data, and invalid child arrays.

The CSS invocation is:

```text
ApiValueTreeBuilder.exe valuetree enrichment\output\css_diagnostics_tree.json "..\..\hi_tools\simple_css" CssDiagnosticData cssdiagnostics_dat
```

This mode is deliberately not named `css-diagnostics`. It can be reused for future embedded HISE datasets without
adding another console application or teaching the builder each domain schema.

The builder must continue to:

- Serialize with `ValueTree::writeToStream()`.
- Generate a header declaration and C++ byte array.
- Print node count and serialized byte size.
- Produce deterministic output for unchanged input.

Generated files:

```text
hi_tools/simple_css/CssDiagnosticData.h
hi_tools/simple_css/CssDiagnosticData.cpp
```

The generated namespace is `CssDiagnosticData` and the data variable is `cssdiagnostics_dat`. Include regeneration
instructions in the generated source header.

### Batch pipeline

Add a fast helper in the API generator submodule:

```text
tools/api generator/buildCssDiagnostics.bat
```

It runs only the Python compile stage and generic ValueTree builder. This allows hint authors to regenerate the blob
without running Doxygen and the complete scripting API enrichment pipeline.

Update `tools/api generator/batchCreateMeta.bat` from six to eight stages:

```text
1. Doxygen XML generation
2. API Phase 0
3. API enrichment merge
4. API binary filtering
5. API ValueTree blob
6. CSS diagnostic validation and normalization
7. CSS diagnostic ValueTree blob
8. MCP scripting API export
```

The full batch file may call `buildCssDiagnostics.bat` for stages 6 and 7 to avoid duplicating commands. Both scripts
must propagate a nonzero exit code when validation or generation fails.

The completion message should state that `XmlApi.h/.cpp`, `CssDiagnosticData.h/.cpp`, and MCP data were regenerated.

### Deterministic generation

Do not include timestamps in the normalized tree or generated C++ files. The pipeline must:

- Sort diagnostic records by stable ID.
- Keep suggestions in authored order.
- Emit ValueTree properties in a fixed order.
- Emit child nodes in a fixed order.
- Normalize generated line endings.
- Print a source hash to the console rather than embedding it in the tree.

### Build integration

HISE uses unity builds. Include the generated `.cpp` from the appropriate `hi_tools` unity source rather than adding
it as an independent project source file.

Guard both declaration and definition according to the actual consumers. Prefer the existing CSS debug-tools guard
if it is available for all required backend paths; otherwise use `#if USE_BACKEND` consistently.

Verify all three configurations conceptually:

| Target | Diagnostic blob |
|---|---|
| HISE IDE | Included |
| Exported plugin | Excluded |
| Project DLL | Excluded |

Do not rely only on link-time dead stripping.

## Runtime database

Add a small `CssDiagnosticDatabase` in `simple_css`.

Responsibilities:

- Lazily deserialize the generated ValueTree once.
- Validate the root type in debug builds.
- Build indexes on first use.
- Match parser events to diagnostic records.
- Instantiate diagnostics with source positions.
- Deduplicate records when requested.

Suggested indexes:

```text
propertyDiagnostics[property]
propertyValueDiagnostics[property][value]
functionDiagnostics[function]
unitDiagnostics[unit]
selectorDiagnostics[selector]
pseudoClassDiagnostics[pseudoClass]
pseudoElementDiagnostics[pseudoElement]
atRuleDiagnostics[atRule]
```

Do not traverse the complete ValueTree for every declaration. ValueTree is the serialized storage and inspection
format, not the hot-path lookup structure.

A function-static database or `SharedResourcePointer` is suitable. The loaded data is immutable after generation.

## Parser integration points

### Declarations

The parser already creates a `RawLine` containing `property` and parsed `items`. After the declaration has enough
syntax to identify its effective form, query:

```cpp
diagnosticDatabase.addForDeclaration(nl, location, diagnostics);
```

This should check:

- Property triggers.
- Property-value triggers.
- Functions used by the value.
- Units used by the value.

Do not emit compatibility hints for declarations that were rejected earlier. Emit the rejection warning instead.

### Selectors and states

After parsing a selector, query selector, pseudo-class, and pseudo-element records. Preserve the selector location so
the diagnostic points to the relevant syntax rather than the start of the rule body.

### At-rules

Query at-rule records while parsing `@import` and `@font-face`. Report unsupported qualifiers or HISE provider
limitations at the most specific location available.

### Existing warnings

Migrate current parser warnings to structured diagnostics incrementally:

- Unsupported keyword warnings.
- Invalid transforms.
- Empty `!important` values.
- Four-digit hash colors.
- Invalid gradients.
- Invalid colors.
- Invalid timing functions.
- Repeated shadow declarations.

Each migrated warning should receive a stable ID and appropriate classification. Logic-dependent warnings may remain
hardcoded in C++; they do not need to be moved into the generated dataset merely for consistency.

## Deduplication

Hints should be deduplicated by diagnostic ID by default. If a stylesheet uses `margin` twenty times, the default
agent response should explain HISE margin semantics once.

The first occurrence should provide the displayed location. The diagnostic may carry an occurrence count:

```json
{
  "code": "hise.css.margin.internal-inset",
  "occurrences": 20,
  "line": 4,
  "column": 2
}
```

Warnings that indicate a discarded declaration should normally retain every location because each location may need
editing.

Provide an internal option for all hint locations so editor integrations can underline every relevant occurrence.

## REST API integration

Update `RestHelpers::handleParseCSS()` to serialize structured parser diagnostics directly.

Each response item should support:

```json
{
  "line": 4,
  "column": 2,
  "length": 6,
  "severity": "hint",
  "source": "css",
  "code": "hise.css.margin.internal-inset",
  "classification": "compatibility",
  "message": "HISE margin reduces the painted area inside fixed component bounds.",
  "suggestions": [
    "Use gap for spacing between flex children."
  ]
}
```

Keep existing response fields stable where possible. Add fields rather than renaming current fields.

Remove location-string parsing for migrated diagnostics. Keep it only for the fatal `Result` error until parser errors
also become structured.

Hints must not set `success` to false.

## hise-cli integration

Update `hise-cli script diagnose_css` to recognize `hint` as a normal diagnostic severity.

Default behavior for agent output:

- Include errors.
- Include warnings.
- Include deduplicated hints.
- Keep the JSON response compact.
- Do not return a failing process status for hints alone.

Potential options:

```text
--hints
--no-hints
--all-hint-locations
```

Hints should be enabled by default for `--agent`, because this is the mechanism that supplies implementation-specific
knowledge. Human output may also enable hints by default, but should render them less prominently than warnings.

The permanent agent guidance can remain short:

> Write normal CSS first, then run `diagnose_css`. Resolve errors and warnings and review HISE-specific hints before
> applying the stylesheet.

## Editor integration

The first milestone only requires parser, REST, and CLI propagation. Editor rendering can follow once the structured
pipeline is stable.

Future editor behavior:

- Render hints with a subdued visual style.
- Show the full message and suggestions on hover.
- Allow suppression by diagnostic ID.
- Request all hint locations rather than deduplicated output.
- Reuse the embedded records for richer CSS completion descriptions.

Do not map hints to `addWarning()` permanently. That would erase the severity distinction introduced by this design.

## Relationship to KeywordDataBase

`KeywordDataBase` currently duplicates some support information:

- Property names.
- Pseudo-classes.
- At-rules.
- Enumerated values.
- Functions.

The first implementation should leave `KeywordDataBase` as the parser and editor keyword source. The diagnostic
database enriches it but does not replace it.

After the hint system is stable, consider generating `KeywordDataBase` tables from the same authored records. That is
a separate refactoring because an error in generated support metadata can change parser and editor behavior, while an
error in diagnostic prose only changes developer guidance.

Build the first record set from the current behavior documented in:

- `guidelines/style/css.md`
- `guidelines/style/css.json`
- `hi_tools/simple_css/LanguageManager.cpp`

For each candidate, verify the current C++ implementation before authoring the message. The style reference is an

Suggested first categories:

### Box model and flex

- Internal margin behavior.
- Synthetic `gap` behavior.
- Paint-only `box-sizing` behavior.
- Local and limited auto sizing behavior.
- Empty or stateful `display: none` behavior.
- No overflow clipping.

### Colors and backgrounds

- Alpha-first eight-digit colors.
- Rejected four-digit colors.
- URL background paint suppression.
- Deferred `background-position` behavior.
- Single-layer background support.

### Text and borders

- Visually solid border styles.
- No font fallback lists.
- Limited text layout and transform behavior.
- Limited generated content grammar.

### Transforms and transitions

- Paint-only transforms.
- No transform origin.
- Rejected matrix and 3D transforms.
- Single transition tuple.
- No transition-driven continuous relayout.

### Selectors, variables, and units

- Limited descendant and specificity behavior.
- Exact combined-state behavior.
- Global variable behavior and no fallback argument.
- Local `vh` behavior.
- `rem` behaving like `em`.

## Implementation phases

### Phase 1: Structured diagnostics

- Add the local CSS diagnostic POD.
- Add `Parser::getDiagnostics()`.
- Convert existing warnings to structured warning diagnostics.
- Preserve `getWarnings()` as an adapter.
- Update `/api/parse_css` to serialize structured warnings.
- Verify existing `diagnose_css` output remains compatible.

This phase should not add compatibility hints yet. It establishes the transport and location model.

### Phase 2: Generated embedded records

- Add `css_diagnostics/diagnostics.json` and its authoring README.
- Add `css_diagnostics.py` validation and normalization.
- Add the generic recursive ValueTree mode to `ApiValueTreeBuilder`.
- Add `buildCssDiagnostics.bat` for fast regeneration.
- Add stages 6 and 7 to `batchCreateMeta.bat` and update all stage counts.
- Generate `CssDiagnosticData.h/.cpp` under the backend or CSS debug-tools guard.
- Add lazy runtime loading and indexed lookup.
- Document both fast and full regeneration commands.

### Phase 3: Parser hint emission

- Add property triggers.
- Add property-value triggers.
- Add function and unit triggers.
- Add selector and at-rule triggers.
- Add deduplication.
- Populate the initial verified hint inventory.

### Phase 4: REST and CLI behavior

- Serialize hint severity, code, classification, suggestions, and occurrence count.
- Update REST endpoint metadata and tests.
- Update `hise-cli` parsing and formatting.
- Ensure hints do not fail diagnosis.
- Add compact agent output.

### Phase 5: Editor enrichment

- Add hint rendering to the CSS editor.
- Add hover descriptions and suppression.
- Consider reusing records for autocomplete documentation.

### Phase 6: Metadata consolidation

- Evaluate generating `KeywordDataBase` from the same source.
- Remove duplicated support lists only if generation is reliable and testable.
- Keep parser behavior in C++ unless a separate data-driven parser redesign is explicitly approved.

## Verification strategy

### Generator verification

- Reject unsupported authored schema versions.
- Reject duplicate IDs.
- Reject unknown severity, classification, and trigger values.
- Reject unknown authored fields.
- Reject missing messages and trigger-specific fields.
- Strip references and notes from the normalized runtime tree.
- Preserve suggestion order while sorting diagnostics by ID.
- Verify generic ValueTree recursion preserves properties and children.
- Verify the legacy scripting API builder invocation remains compatible.
- Verify deterministic generated output.
- Verify the serialized tree deserializes and has the expected root type.
- Report record count and byte size.
- Verify `buildCssDiagnostics.bat` and `batchCreateMeta.bat` propagate generation failures.

### Parser verification

- A standard supported declaration produces no hint.
- Each trigger type emits the expected diagnostic.
- Rejected declarations do not also emit compatibility hints.
- Warning locations point to the affected declaration.
- Selector hints point to selector syntax.
- Default hint deduplication reports one item per ID.
- All-location mode reports each occurrence.
- Hints never change parsed stylesheet values.
- Hints never change parser success.
- File, inline-code, and component diagnosis emit the same hints for the same CSS syntax.

### REST verification

- Existing error and warning fields remain available.
- Hint severity serializes as `hint`.
- Codes, classifications, suggestions, and locations round-trip.
- Hints alone return `success: true`.
- File, inline-code, selector-resolution, and component modes all preserve diagnostics.

### Build configuration verification

- HISE IDE includes and can deserialize the blob.
- Exported frontend builds do not include the blob or lookup implementation.
- Project DLL builds do not include the blob.
- The parser continues to function in non-backend builds without diagnostic data.

### Agent workflow verification

Use representative CSS written with browser assumptions and verify that one diagnosis call reports the relevant HISE
differences without returning the entire reference dataset.

Example input:

```css
.container
{
	display: flex;
	overflow: hidden;
}

.item
{
	margin: 10px;
	opacity: 0.5;
	transform: translateX(20px);
}
```

Expected findings:

- Warning for ineffective overflow clipping.
- Hint for internal margin behavior.
- Hint for approximate opacity behavior.
- Hint for paint-only transform behavior.

No ordinary reference entries should be returned for `display: flex` or numeric values.

## Acceptance criteria

The initial feature is complete when:

- `simple_css::Parser` exposes structured errors or warnings and hints through one diagnostic collection.
- Human-editable diagnostic records are tracked in `tools/api generator/css_diagnostics/diagnostics.json`.
- `css_diagnostics.py` validates and converts the authored records to generic ValueTree JSON.
- `ApiValueTreeBuilder` supports the reusable recursive `valuetree` mode without breaking its API mode.
- `buildCssDiagnostics.bat` provides a fast regeneration path.
- `batchCreateMeta.bat` regenerates the CSS diagnostic blob as part of its full pipeline.
- A generated ValueTree containing HISE compatibility records is embedded in backend HISE builds.
- The dataset is loaded lazily and indexed before matching.
- The parser emits records only for syntax present in the stylesheet.
- Errors, warnings, and hints retain distinct severities through `/api/parse_css`.
- `hise-cli script diagnose_css` displays hints in agent output.
- Hints do not fail diagnosis or alter stylesheet behavior.
- Repeated hints are deduplicated by stable ID by default.
- Exported plugins and project DLLs do not contain the diagnostic blob.
- The documented agent workflow requires only one diagnosis call after drafting CSS.

## Deferred decisions

The following are intentionally outside the first implementation:

- Making parser grammar data-driven.
- Replacing all `KeywordDataBase` tables with generated data.
